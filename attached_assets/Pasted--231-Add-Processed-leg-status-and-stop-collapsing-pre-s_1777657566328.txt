#231 - Add "Processed" leg status and stop collapsing pre-submit legs

What & Why

Today, the claim-status projector (macroPhaseToStatus in artifacts/api-server/src/lib/denormalized-cache.ts:35-45) collapses every leg in an invoice down to a single representative status derived from the parent group's macro phase:

Group's macro phase	Group statuses in phase	Projector writes to leg	Verdict
pre-submit	New, Needs Evidence	Needs Evidence	Wrong — see below
in-flight	Portal Queued, Generating Email, Awaiting Response	Awaiting Response	OK — confirmed acceptable
response-pending	Ready to Review, Needs Review	Needs Review	OK
mas-action-required / awaiting-payout	(group still Resolved)	Resolved	OK
closed	Resolved, Denied, Withdrawn	Resolved	OK
on-hold	On Hold	On Hold	OK
The pre-submit collapse is the real bug. There's no per-leg signal telling an operator "this leg has been worked through — I'm waiting for its siblings before the invoice can be packaged." Every leg in a pre-submit invoice reads Needs Evidence regardless of whether the operator has actually run the SOP/worktree on it. So the operator can't open the Queue and see at a glance which legs in an invoice still need their attention vs. which are done — they all look the same.

The codebase already has the per-leg state needed to compute this correctly. claims.sop_outcome (lib/db/src/schema/claims.ts:91 — portal_dispute | dispute | hold | cannot_dispute | non_issue | NULL) records the outcome of running the SOP worktree on a leg. deriveLegSubStatus (artifacts/api-server/src/routes/claims.ts:204-260) already projects this into a per-leg sub-status (investigating | ready | blocked | excluded | submitted). What's missing is surfacing the "ready" sub-status — the post-worktree, pre-submission state — at the claim.status level so it shows up in tabs, filters, lists, and the claim row itself.

This task does two things:

Add a "Processed" value to the claim_status enum and make the projector write it onto any leg whose SOP worktree has been completed and is now waiting for the invoice as a whole to be packaged. Concretely: when a leg's sub-status is "ready" (sop_outcome ∈ ('portal_dispute','dispute'), no per-leg hold, not yet submitted), claim.status becomes "Processed". Operators get a single per-leg signal: anything still showing New or Needs Evidence in the invoice still owes worktree attention.
Surface a "Ready to package" CTA on the invoice group when every leg in the group is either "Processed" or excluded (sop_outcome ∈ ('cannot_dispute','non_issue')) or held (sop_outcome = 'hold' or hold_reason set — held legs are tracked separately and don't block packaging). The CTA is operator-driven — clicking it advances the group out of pre-submit into the existing Generating Email flow (no auto-advance). This gives the operator the explicit "pull the trigger" moment the workflow has been missing.
The downstream effect on the original urgency-mismatch symptom: the in-flight projection (Portal Queued / Generating Email / Awaiting Response → leg Awaiting Response) stays as-is and remains correctly excluded from the leg-level on-clock filter. The pre-submit projection becomes either New, Needs Evidence, or Processed — all of which need to be in the on-clock set so the Queue and Claims-list urgent counts match the dashboard's group-level count for pre-submit groups.

Done looks like

The claim_status enum has a new "Processed" value, added at the database level via migration.
A leg whose SOP worktree concluded with a dispute outcome and no hold has claim.status = "Processed" everywhere it's surfaced (Queue, Claims list, claim detail, CSV export, audit context).
A leg in a pre-submit invoice that has NOT yet been worked through still reads New or Needs Evidence, so operators can sort/filter to find unfinished work in an invoice.
Excluded legs (sop_outcome ∈ ('cannot_dispute','non_issue')) do not get stamped "Processed" — they keep whatever closed/withdrawn status they already carry.
Held legs continue to read "On Hold" regardless of sop_outcome; per-leg holds are preserved across projector runs.
Legs in in-flight groups (Portal Queued / Generating Email / Awaiting Response) keep reading Awaiting Response — the in-flight collapse stays.
The Queue and Claims list show per-leg urgency for pre-submit legs (New, Needs Evidence, Processed, On Hold) that match the dashboard's count for the same invoice groups.
An invoice group's right-side panel (in the Queue) and its detail page show a "Ready to package" CTA exactly when every leg is Processed-or-excluded (held legs ignored, no leg still New/Needs Evidence/investigating). The CTA is disabled with a clear reason otherwise (e.g. "3 legs still need worktree review").
Clicking the CTA advances the invoice group from its current pre-submit status (New or Needs Evidence) to Generating Email via a new system-controlled transition, with the existing audit/lock/presence semantics. No auto-advance fires from leg edits — the operator is always the one who clicks.
A regression test fails today and passes after the fix, proving (a) the per-leg "Processed" projection is correct for every sub-status case and (b) the CTA's enable/disable logic matches the rule above.
Out of scope

Any new automation that fires the CTA without operator click — explicit operator action only.
Reworking the in-flight projection (Portal Queued / Generating Email / Awaiting Response → Awaiting Response) — confirmed acceptable.
Reworking the response-pending or closed-phase projections — out of scope for this task.
Changes to EXPIRING_ACTIONABLE_STATUSES, the 30-day window, the weekend-shift rule, or SOON_DAYS/URGENT_DAYS.
Changes to per-leg hold semantics, sop_outcome semantics, or the SOP worktree itself.
Reworking how the Queue page surfaces unprocessed legs visually — that lives in Task #232 (Classification Inbox restructure). This task gives #232 a richer per-leg signal to key off of, but does not restructure the Queue page.
Audit of every claim.status consumer (decisions per site)

The grep below was run over artifacts/api-server/src excluding tests. Each call site is annotated with the decision under the new model.

A. The projector (the only writer — must change)

lib/denormalized-cache.ts:35-92 macroPhaseToStatus + the call site in refreshClaimDenormalizedCache. Replace. New rules, applied in this order:
If leg.holdReason != null OR leg.sopOutcome === 'hold' → On Hold. (Per-leg hold preserved across all projector runs.)
Else look at the parent group's macro phase:
pre-submit (group.status ∈ {New, Needs Evidence}) → leg gets a value derived from sop_outcome:
sop_outcome IN ('portal_dispute','dispute') → Processed (new value).
sop_outcome IN ('cannot_dispute','non_issue') → leg keeps its closed/withdrawn status (don't overwrite).
sop_outcome IS NULL → mirror group's status (New or Needs Evidence).
in-flight (group.status ∈ {Portal Queued, Generating Email, Awaiting Response}) → Awaiting Response (collapse retained — confirmed acceptable).
response-pending (group.status ∈ {Ready to Review, Needs Review}) → mirror group's status.
mas-action-required / awaiting-payout / closed → mirror group's status (typically Resolved).
on-hold (group.status = On Hold) → On Hold.
Standalone legs (no invoice_group_id) keep their existing status.
refreshClaimDenormalizedCache must be re-triggered when sop_outcome flips (the existing call sites that mutate sop_outcome are in routes/claims.ts SOP-advance handlers — verify each one already calls the refresh and add the call where it's missing).

lib/expiring-filter.ts:31-39 — derives from EXPIRING_ACTIONABLE_STATUSES. No change.

lib/group-transitions.ts:117-121, 133-139, 170-179, 374-383, 525-536 — all use claim.status = "On Hold" (or != "On Hold") as proxy for "is this leg held?". Under rule A.1 the projector preserves per-leg holds, so these predicates remain correct. No predicate change.
D. Manual-transition guards

VALID_MANUAL_STATUS_TRANSITIONS["Processed"] = ["Needs Evidence", "On Hold", "Resolved", "Denied"] — operator can drop a leg back to Needs Evidence if they made a mistake, place it on hold, or close it as resolved/denied.

routes/claims.ts:564,568,591,607 — read those tables directly. No change once D is updated.

H. Backfill

One-time migration that updates every existing claims.status to match the new projection rules. Specifically:
For legs in a pre-submit group with sop_outcome IN ('portal_dispute','dispute') and no per-leg hold → set claim.status = 'Processed'.
For legs in a pre-submit group with sop_outcome IS NULL and no hold → ensure claim.status matches the group's status (New or Needs Evidence).
Leave held legs and excluded legs alone.
For legs in in-flight / response-pending / closed groups — re-derive via the projector to ensure consistency with the new rules.
Idempotent and re-runnable. Audit-log the backfill so the per-leg history reads Status changed from X to Y (backfill #231).
I. CTA endpoint and UI

New backend route, POST /invoice-groups/:id/package (or similar — match the existing route conventions in routes/invoice-groups.ts), guarded by:
Group is in New or Needs Evidence.
Every leg in the group has sop_outcome IS NOT NULL OR hold_reason IS NOT NULL (held legs don't block packaging — they're tracked separately).
At least one leg has sop_outcome IN ('portal_dispute','dispute') (don't package an invoice with zero contestable legs).
The route runs transitionGroupStatus to move the group to Generating Email with source = 'operator_packaged' and the standard audit/lock/presence semantics.
New backend helper that returns, for a group, the readiness state: { ready: boolean, reason: string, unprocessedLegCount: number, processedLegCount: number, excludedLegCount: number, heldLegCount: number }. Surface this on the existing GET /invoice-groups/:id response so the frontend can render the CTA's enabled/disabled state and tooltip without a separate fetch.
Frontend: render the CTA on (a) the invoice-group detail page (InvoiceGroupDetailV2) and (b) the Queue right-side panel (Task #232 will own the panel restructure but should pick up this CTA from the same backend payload). Disabled state shows the readiness reason ("3 legs still need worktree review").

## A. Unknown / requires_human_decision

### A1. `closure-data-foundation.test.ts` — closure-data cascade contract

- **Where:** `artifacts/api-server/src/__tests__/closure-data-foundation.test.ts`
- **Failing assertion (per Phase 1 audit):** `closure_data` denormalized
  cache must populate within the same transaction as the closing
  `transitionGroupStatusAndOutcome` write.
- **Expected:** closure-data row present immediately after the helper
  returns.
- **Actual:** closure-data row absent until the next `denormalized_cache`
  refresh cycle runs.
- **Why human-needed:** The Phase 1 audit could not determine whether
  this is (a) a product regression (the helper was supposed to call the
  cache refresh inline and stopped doing so), or (b) a deliberate
  decoupling (closure-data is now an async denorm step, intentionally
  eventually-consistent). The contract map (§3.2) says
  "denormalized cache is refreshed by `recomputeDenormalizedCacheForGroup`
  after every successful transition" — but does not specify *inside* vs.
  *after* the txn. Either reading is defensible.
- **Owner question (for whoever owns lib/denormalized-cache.ts):**
  Should `closure_data` be visible at the moment a closing transition
  helper returns, or is one cache-refresh tick of lag acceptable? If the
  former, the helper needs an inline call; if the latter, the test
  should poll/await the refresh.

### A2–A4. `attestation-queue-endpoints.test.ts` — three 409 envelopes

- **Where:** `artifacts/api-server/src/__tests__/attestation-queue-endpoints.test.ts`
- **Failing assertions (3 sibling tests):**
  - `POST /attestation-queue/:id/queue` returns 409 when the parent
    group has already stamped `reattestCompletedAt`.
  - `POST /attestation-queue/:id/complete` returns 409 when the leg's
    `attestation_state` is not `pending`/`queued`.
  - `POST /attestation-queue/:id/dequeue` returns 409 when the leg is
    already `completed`/`not_required`.
- **Expected:** the 409 envelopes carry the legacy
  `error: "..."` + `expectedState: "<state>"` + `actualState: "<state>"`
  shape these tests assert.
- **Actual (per Phase 1 audit):** the routes now return a generic
  `{ error: "<msg>" }` envelope without the structured `expectedState` /
  `actualState` fields.
- **Why human-needed:** This mirrors the Hotfix #635 envelope-shape
  change on payor-denial-reason / awaiting-payor-again (which we DID
  edit, because the contract map §2.4 explicitly cites the new shape).
  The contract map does NOT cite a sibling change for the attestation
  queue. Either:
  - (a) the attestation queue routes were intentionally NOT migrated to
    the structured envelope (they're admin-tier, stricter consumers),
    in which case these tests are correct and the route change is the
    drift; or
  - (b) the migration is in flight and the contract-map omission is
    itself the drift.
- **Owner question (for whoever owns lib/attestation.ts +
  routes/attestation-queue.ts):** Are these 409 envelopes supposed to
  carry the same `expectedState`/`actualState` shape that #635
  introduced for the response-pending gates? If yes — fix the routes;
  if no — update these tests to match the new envelopes (and document
  in the contract map §2.5).

## B. Order-dependency / shared-state observations (not edited)

### B1. `shared-batch-view.test.ts` — order_dependency

- **Where:** `artifacts/api-server/src/__tests__/shared-batch-view.test.ts`
- **Symptom (Phase 1 audit):** the test passes in isolation
  (`pnpm --filter @workspace/api-server test shared-batch-view`) but
  fails when the full suite runs in `--test-concurrency=1` mode after
  certain neighbors. The audit traced the leakage to the shared
  `batch_views` table being updated by a sibling test
  (`response-tracker-batch.test.ts`) that does not clean up its
  per-batch row.
- **Why not edited in Phase 2:** Phase 2's scope is "tests whose
  assertions misread the current product contract." Order-dependency
  bugs are a harness issue (test isolation), not a contract drift —
  fixing them requires either:
  - adding a `before`/`after` hook in `shared-batch-view.test.ts` that
    reseeds the table (acceptable but masks the sibling's leak), or
  - fixing the sibling's cleanup (correct but out of Phase 2's
    "no product code, no quarantining" guardrails — and arguably a
    sibling-test fix is also out of scope).
- **Recommended next phase:** add this to the dedicated stress-harness
  / order-dependency phase. The audit's reproduction recipe is in the
  Phase 1 report under `shared-batch-view :: order_dependency`.

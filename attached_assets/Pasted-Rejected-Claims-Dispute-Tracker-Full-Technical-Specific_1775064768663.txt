Rejected Claims Dispute Tracker — Full Technical Specification
1. APPLICATION OVERVIEW
This is an internal tool for a non-emergency medical transportation (NEMT) company to manage rejected ride claims from payors (insurance companies like MAS). It automates the dispute process: importing rejected claims, guiding staff through evidence collection using decision-tree workflows, generating AI-powered dispute emails, sending them via Outlook, tracking responses, and submitting portal-based disputes.

Tech Stack: React + Vite, TailwindCSS, shadcn/ui, TanStack React Query, React Router v6. Backend: Deno-based serverless functions. Database: Entity-based (Base44 BaaS). Email: Microsoft Graph API via Outlook OAuth connector.

3. DECISION TREE MODEL
3.1 Data Structure
Stored as JSON string on ErrorType.decision_tree:

{
  "nodes": [
    {"id": "start", "type": "question", "label": "Is GPS data available?", "options": ["Yes", "No"]},
    {"id": "node_2", "type": "action", "label": "Upload GPS screenshot"},
    {"id": "node_3", "type": "hold", "label": "Pending GPS review", "hold_default_reason": "...", "hold_default_pending_from": "...", "hold_instructions": "..."}
  ],
  "edges": [
    {"from": "start", "to": "node_2", "label": "Yes"},
    {"from": "start", "to": "__outcome__", "label": "No", "outcome": "internal"},
    {"from": "node_2", "to": "__outcome__", "label": "", "outcome": "portal_dispute"}
  ]
}
3.2 Node Types
question: Branching decision point. Has options array (e.g. ["Yes", "No"]). Each option is a label for an outgoing edge.
action: An action staff must perform. Single "Continue" button. Can optionally have evidence_requirements array for node-specific evidence.
hold: Terminal node — places claim on hold. Has hold_default_reason, hold_default_pending_from, hold_instructions.
3.3 Outcome Edges (Terminal Branches)
Instead of terminal nodes, leaf branches use special edges with "to": "__outcome__":

"outcome": "portal_dispute" — Submit via MAS portal (PRIMARY dispute method)
"outcome": "dispute" — Send dispute via email (fallback)
"outcome": "internal" — Resolve internally, no external dispute
3.4 Legacy Migration
Old trees had "type": "end" (mapped to dispute) and "type": "internal" nodes. The migrateTree() function converts these to the new edge-outcome model. Migration runs automatically when an admin opens an error type for editing.

3.5 Workflow Progress
Stored on Claim.workflow_progress as JSON:

{
  "currentNodeId": "node_5",
  "history": [
    {"nodeId": "start", "nodeLabel": "Is GPS data available?", "answer": "Yes", "timestamp": "..."},
    {"nodeId": "node_2", "nodeLabel": "Upload GPS screenshot", "answer": "Completed", "timestamp": "..."}
  ],
  "completed": true,
  "resolution_type": "portal_dispute"
}

5. BACKEND FUNCTIONS
5.1 importClaims
Input: {file_url, duplicate_action: 'skip'|'update'}
Uses AI extraction (ExtractDataFromUploadedFile) to parse Excel/CSV
Creates claims with status New, outcome Pending
Duplicate detection by conf_number
Returns: {created, skipped, updated, duplicates, batch_id}
5.2 generateDisputeEmail
Input: {claim_id, selected_reason_id}
Sets claim status to Generating Email
Fetches claim, error type, mailbox config, evidence
Builds detailed prompt including dispute reason from library and evidence descriptions
Calls InvokeLLM for subject + body generation
Saves to claim fields, sets status to Ready to Review
5.3 sendDisputeEmail
Input: {claim_id, to_email, subject, body}
Uses Outlook OAuth connector (connectors.getConnection('outlook'))
Sends via Microsoft Graph API: POST https://graph.microsoft.com/v1.0/me/sendMail
Supports shared mailbox (sets from field from MailboxConfig)
Updates claim status to Awaiting Response, creates Note
5.4 bulkSendEmails
Input: {claim_ids: string[]}
Iterates claims, sends each via SendEmail integration (not Outlook directly)
Staggers delivery: 1-3 second random delay between emails
Uses MailboxConfig.payor_email as fallback recipient
Returns: {sent, failed, errors}
5.5 parseReplies
Uses Outlook OAuth to fetch last 50 inbox messages from shared mailbox
Matches emails to claims with status Awaiting Response by conf_number or ref_number in subject/body
Extracts invoice numbers via regex: /(?:invoice\s*#?|inv[-\s]?)(\w{4,12})/gi
Creates Note of type reply_parsed, updates claim
5.6 testOutlookConnection
Simple test: calls GET https://graph.microsoft.com/v1.0/me with OAuth token
Returns email and display name to verify connection
5.7 dailyBriefEmail
Scheduled automation (runs daily at 10:00 UTC = 6:00 AM ET)
Computes pipeline overview, expiration risks, recent replies
Sends styled HTML email to all users
Returns summary of what was sent
5.8 portalSubmissions
External bot API with actions:
poll → returns pending submissions (up to 20)
claim → marks submission as in_progress
complete → marks as submitted, updates claim to Awaiting Response, creates Note
fail → marks as failed with error message
create → creates new submission from claim data (copies all relevant fields, builds attachment list from evidence)
list → lists submissions with optional status filter
All actions require authenticated user

8. KEY COMPONENTS
8.1 WorkflowPlayer
Interactive decision tree executor. Renders current node (question/action/hold), tracks history as breadcrumbs, saves progress to claim. Shows completion state based on resolution_type.

8.2 EvidencePanel
Dynamic evidence collection form. Requirements sourced from (in priority order):

Current workflow node's evidence_requirements
ErrorType's evidence_requirements
Keyword-matched defaults from lib/constants.js
Supports file uploads and text inputs. Progress bar shows completion.

8.3 DecisionTreeBuilder
Visual editor for building decision trees. Supports creating/editing/deleting nodes, connecting edges, setting outcomes on leaf branches. Uses OutcomeSelector for terminal branches.

8.4 SOPAnalyzer
AI-powered SOP document analyzer. Uploads PDFs/images, calls LLM to extract structured data (decision tree, dispute reasons, evidence requirements). Uses claude_sonnet_4_6 model (higher credit cost).

8.5 PortalSubmissionPanel
Form for queuing MAS portal submissions. Pre-fills from claim data. Fields map to MAS portal form: issue type, subject, email, provider name, phone, invoice, GPS breadcrumbs, description. Calls portalSubmissions create action.

8.6 DisputeReasonPicker
Lets staff select from pre-configured dispute reasons (from ErrorType library) or create new ones on the fly. Selected reason ID is passed to generateDisputeEmail.

8.7 EmailReviewPanel
Review/edit/regenerate AI-generated email before approval. Can edit subject and body inline.

8.8 BulkSendBar
Sticky bottom bar for batch-sending approved emails with count and total value display.

8.9 Presence System (usePresence hook)
Creates PresenceLog record on mount, deletes on unmount
Heartbeat every 15 seconds
Stale threshold: 45 seconds
Uses real-time subscriptions for instant updates
8.10 Audit System (useAuditLog hook)
Logs "viewed" action once per mount
logAction(action, details, metadata) creates AuditLog entries
Fetches and caches logs per claim
9. EVIDENCE SYSTEM
9.1 Requirement Sources (priority order)
Node-level: Specific workflow nodes can have evidence_requirements array
ErrorType-level: ErrorType.evidence_requirements JSON
Keyword defaults: Match error text against GPS, attestation, time, duplicate keywords
9.2 Default Requirements
Defined in lib/constants.js:

GPS: GPS screenshot, trip coordinates, GPS context notes
Attestation: Signed form, attestation details
Time: Trip log screenshot, time explanation
Duplicate: Trip records comparison, explanation
Default: Supporting doc, dispute explanation
10. 30-DAY EXPIRATION SYSTEM

Summary: Full expiration risk analysis
Daily brief email: Expired + expiring lists

#232 - Queue Page Restructure

What & Why

The Queue page has drifted from being a place where an operator can rip through dispute work efficiently. Three things are broken:

Classification Inbox is noisy and inaccurate. It lists every "Needs Review" invoice group with no group-level error_type_id, producing 100+ entries — but the unit of work is wrong. Most invoice groups have one claim with the actual rejection and several clean siblings that don't need any classification at all.
Responses Awaiting Review is duplicated on the Queue page even though it has its own nav entry and Dashboard surface.
The right-side workflow panel was gutted in a prior cutover (see the "Task #199 / post-cutover" comment in queue.tsx). It used to host the full dispute workflow inline; now it's a stub card whose only meaningful action kicks the operator out to /invoice-groups/:id. That secondary screen has many paths out and breaks the "stay on the Queue and burn down the list" workflow.
This task fixes all three on the Queue page in one cohesive pass. The model shift is consistent: invoices are the whole; claims are the parts. Work is tracked at the claim level; an invoice becomes ready to submit only when every one of its claims is in a terminal state.

Soft assumption — processed claim status

This task assumes a claim-level status value of processed exists (being introduced in a separate parallel effort), meaning "this claim's workflow is complete and it is waiting on its sibling claims and the invoice-level submission." The right-side panel uses this status (alongside excluded_at and terminal sop_outcome) as the per-claim "terminal" signal that drives the invoice's readiness to submit. If naming or semantics shift in the parallel effort, the implementer should align — but the architecture here treats processed as a real claim status, not a derived flag.

Done looks like

Classification Inbox

The card on the Queue page is collapsible and defaults to collapsed, with the accurate count visible in the collapsed header.
Inbox rows are at the claim level, visually grouped under their parent invoice. The badge shows the total number of qualifying claims across visible groups.
Counts and surfaced rows follow the qualifying-claim rule (defined under Steps).
After the change, an operator who previously saw 100+ entries sees only the claims that genuinely need classification — typically a sharp drop.
When the rule produces zero claims, the collapsed header shows a subdued "No claims to classify" line with no chevron.
Sibling-cleared blank claims are auto-resolved at the data layer

When a "Needs Review" invoice transitions out of Needs Review, the server auto-excludes any blank-description claims on that invoice as non_issue via the existing useExcludeLeg mutation path — but only when at least one sibling on the same invoice has an error description. This produces a real excluded_at + reason=non_issue write and a real leg_excluded audit log entry for each auto-cleared claim. UI and data agree; downstream reports see the same picture.
The all-blank case (no claim has an error description) is not auto-resolved. Those claims are surfaced in the inbox and the operator decides each one manually as non-issue or non-contestable.
Responses Awaiting Review

The "Responses Awaiting Review" card is gone from the Queue page entirely. The left-nav entry and any Dashboard surface remain untouched.
All Queue-page state, handlers, refs, helper text, and imports tied exclusively to that card are removed (selectedResponseReviewId, selectResponseReview, responseReviewGroups, the <QueueResponseReviewPanel> render block, the "Responses Awaiting Review above" copy in tab descriptions, and any now-unused imports such as ResponseReviewRowMeta).
The QueueResponseReviewPanel component itself is preserved — it's still consumed by responses-awaiting-review.tsx.
Workflow tabs

The Awaiting tab is removed from the Queue page (it's not actionable from here). Its useListInvoiceGroups({ status: "Awaiting Response" }) query is removed.
Action Required, Portal Queued, and On Hold remain in that order.
VALID_TABS is updated; ?tab=awaiting URLs fall back to the default tab silently.
Right-side workflow panel — the inline workspace

When an operator selects an invoice group from any tab, the right-side panel becomes a real workspace where they can complete the dispute end-to-end without leaving the Queue page:

Header: invoice number, status, LegSubStatusPill counters, a compact "X of Y claims processed" progress indicator (counts every claim in a terminal state — processed, excluded_at set, or terminal sop_outcome — over total claims), and a small "Open full detail page" link to /invoice-groups/:id as an escape hatch.
Related claims list for the selected invoice group, ordered by leg sequence, showing each claim's status, whether it has an error_details value, its current error_type_id, and per-row controls below.
Blank-description claims (sibling-cleared) render read-only with an "Auto: non-issue (no rejection on file)" badge. No buttons, no expansion. They were already excluded server-side at Needs Review → Needs Evidence transition; the panel reflects that fact.
Blank-description claims on an all-blank invoice render with two manual buttons — Mark non-issue and Mark non-contestable — that call useExcludeLeg with the new reason values. Both write a leg_excluded audit entry.
Claims with an error description that aren't yet processed are the operator's primary work. Each row expands inline to host the full per-claim workflow (assign/refine error_type_id, run the SOP via SopAdvancePlayer, edit per-leg context, place on hold / clear hold, exclude/include) using the same hooks the detail page uses. Completing the per-claim workflow flips that claim to processed.
Aggregate context editor: the same group-context + per-leg roll-up section currently rendered in invoice-group-detail-v2.tsx lines ~214–292, lifted into a shared subcomponent and rendered inside the panel.
Submission gauntlet (Understanding Readback → Generate Preview → Submit to Portal): the same workflow gate currently in invoice-group-detail-v2.tsx lines ~369–547, lifted into a shared subcomponent. Locked until every claim on the invoice is terminal (i.e., processed OR excluded_at IS NOT NULL OR terminal sop_outcome). While locked, the gauntlet shows a clear "X claims still need to be processed before this invoice can be submitted" message and a one-click "Jump to next unprocessed claim" affordance. When all claims are terminal, the gauntlet unlocks and the operator can readback → preview → submit without leaving the Queue.
Lock / presence: the existing HumanPresenceBanner and lockReason (from othersPresent) disable every mutating control inside the panel, not just the workspace link.
Real-time updates: the panel re-renders on useInvoiceGroupEvents for the selected group, so another user's changes (or the auto-exclusion completing) don't leave the panel stale.
State preservation: switching tabs no longer clears selectedWorkflowId. Selection survives tab changes and is reflected in the URL (?group=) so refresh and link-sharing both work.
Layout: at lg and up, when a group is selected the right column gets at least 2/3 of the row width (master/detail proportions); at md and below, the panel stacks under the list as it does today.
Auto-select: when there's exactly one row across the visible tab and nothing is selected, auto-select it. Otherwise show the existing "Select an invoice group to process" empty state.

Steps

A. Classification Inbox — claim-aware rule

Define the qualifying-claim predicate. A claim is "qualifying" (i.e., needs classification) when:
its parent invoice group is in status Needs Review, and
the claim is not excluded (excluded_at IS NULL) and has no terminal sop_outcome, and
either error_details is non-null and non-empty (after trim) AND error_type_id IS NULL,
or every claim on the parent invoice has empty/null error_details (the all-blank case — surface every blank claim for research). When evaluating "every claim on the invoice has empty error_details," ignore claims that are excluded or have a terminal sop_outcome.
Add a server-side classification summary. Extend GET /invoice-groups (the endpoint behind useListInvoiceGroups) with an opt-in query parameter include=needs_classification that, when set and status=Needs Review, returns per group: { qualifyingClaimIds: number[], totalQualifyingClaims: number, allBlank: boolean }. The total across all groups becomes the new inbox badge count. Do not change the default response shape.
Rewrite Classification Inbox state on queue.tsx. Replace unclassifiedGroups = needsReviewGroups.filter(g => !g.errorTypeId) with a derived list driven by the new server field. Render rows at the claim level, grouped under invoice headers, ordered by oldest first-service date. The badge count = sum of totalQualifyingClaims across visible groups.
Rework the triage panel's contract. Today QueueNeedsReviewPanel calls useTriageInvoiceGroup (POST /api/invoice-groups/:id/triage), which sets invoice_groups.error_type_id and forces status to Needs Evidence. Update the flow:
Add a per-claim "Assign Error Type" affordance to inbox rows. Each Assign mutation sets the claim's error_type_id via the existing useReclassifyLeg mutation (preserves audit).
Keep QueueNeedsReviewPanel's "Assign to all qualifying claims on this invoice" as a one-click shortcut that fans out the per-claim mutation across the qualifying set.
For the all-blank case, the inbox row exposes the manual non-issue / non-contestable buttons (writing excluded_at + reason via useExcludeLeg with the new reason values).
A claim is "resolved for the purpose of leaving Needs Review" when it has either error_type_id set or excluded_at set. The group's Needs Review → Needs Evidence transition fires when no qualifying claims remain unresolved. Move the status advancement into lib/group-transitions.ts (the existing auto_after_classify path) and remove the UI-side forced status update so the transition happens server-side via transitionGroupStatus (preserving audit).
For backward compatibility with invoice_groups.error_type_id: when the "Assign to all" shortcut produces a single error type across all qualifying claims, also write that value to invoice_groups.error_type_id. When per-claim assignments diverge, leave the group field null.
For the all-blank invoice case, after every blank claim is manually excluded, the group's transition target is whatever the existing transition logic resolves to when the included-leg count drops to zero (likely a Resolved/Withdrawn outcome rather than Needs Evidence). Verify and document the chosen behavior; do not invent a new state.
Server-side auto-exclusion of sibling-cleared blanks. Inside lib/group-transitions.ts, on the Needs Review → Needs Evidence transition, look for blank-description claims whose siblings include at least one claim with non-empty error_details. For each such claim, perform the same excludeLeg operation that the API endpoint performs, with reason = non_issue, attributed to a system actor. This must:
Fire the leg_excluded audit entry for each auto-excluded claim.
Be idempotent (re-running the transition logic must not double-exclude).
Be a single transactional unit with the status transition itself (either both happen or neither).
Not run on the all-blank case. Add a single integration test that walks an invoice with mixed described/blank claims through Needs Review → Needs Evidence and asserts the correct excluded_at writes and audit entries.
Make the inbox card collapsible, default collapsed. Wrap the inbox in the existing collapsible primitive (match its aria-expanded / focus pattern). Persist the expand/collapse choice in the URL (?inbox=open) so refresh keeps the operator's preference for the session. When the count is 0, render a one-line subdued header with no chevron / no expand action.
Empty / loading copy. Inbox loading: keep the existing triageLoading shim. Inbox empty (count 0): "No claims need classification right now." Inbox helper text on expand: a one-sentence plain-language description of the rule ("Showing claims with a rejection reason that aren't yet classified, plus claims on invoices where no rejection was returned at all.").

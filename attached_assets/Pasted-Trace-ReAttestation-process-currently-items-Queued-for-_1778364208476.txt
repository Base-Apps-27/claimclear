Your intuition, restated technically
Right now the system has two parallel state vocabularies:

Group level: status (free‑form enum: "Ready to Review", "Needs Review", "MAS Eligible", "Closed", …), phase (derived but sometimes stored), reattestRequired, reattestCompletedAt, awaitingPayorAgainAt.

Every recurring bug we've had on this surface is the same shape: two writers, one reader, different vocabularies. Bug #1 from my last message is exactly that — response-tracker writes "Ready to Review", the gate reads "Needs Review". Task #547 was the same shape. So yes — the real disease is "too many overlapping status fields, multiple writers per field, gates that string‑match instead of asking a question." Your instinct is correct.

Where I'd push back on "why gate at all?"
Gates aren't there to annoy operators. They exist for three real reasons, and we can't just delete them:

Concurrency. Two operators on the same invoice can't both queue it for re‑attest at the same moment (Task #92 was about exactly this). The gate is the lock.
External reality. "Re‑attestation complete" means MAS acknowledged the survivor legs. That's a real‑world event with a real‑world ordering — you can't mark a group "complete" before MAS has been told. The gate enforces the order.
Audit. Each transition writes a state event + audit row. Without a gate, a re‑click or a stray webhook double‑counts.
But — and this is the important part — none of those reasons require the gate to be a string match on group.status. The gate just needs to ask: "Is this transition legal given the current shape of the legs?" That's exactly the simplification you're proposing.

The cleanest path forward (what I'd actually recommend)
Move to one invoice state machine, derived from leg facts, with named transitions. Concretely:

A. Collapse to a single source of truth per concept
Leg facts (what an operator actually decided) stay on the leg: outcome, disposition, includedInDispute. These are inputs.
Invoice state becomes one enum, derived in one function from leg facts + a small number of timestamps (submittedAt, responseReceivedAt, reattestQueuedAt, reattestCompletedAt, closedAt, holdAt). No more status and phase and macroPhase.
Delete group.status as a writable field. It becomes a computed view.
B. Replace string‑match gates with a transition table
One file says: from state X, given leg shape Y, you can move to state Z. Both server and client import the same table — no more "must move together" comments hoping three implementations agree.

C. Make the operator UX a thin shell over the transition table
The "What's next" card just lists legal transitions for the current state. If a transition isn't listed, it isn't offered — there's no separate "is the button enabled?" logic to drift.

D. Where you're slightly oversimplifying
"once all legs are defined the Invoice should change to a state where it can move to Reattest or closed out"

Almost. Two wrinkles:

"All legs defined" isn't a single bit. A leg can be Approved, Denied, Non‑issue, Withdrawn, Duplicate, or Cannot‑Dispute — and which combinations imply "Re‑attest" vs "Close" vs "Dispute first then re‑attest" is the actual business logic that lives in deriveInvoiceDisputeOutlook today. That logic is fine; it just needs to be the only place that decides, instead of being mirrored in three other gates.
MAS round‑trip is real. For invoices that need MAS acknowledgement before re‑attest, "ready to re‑attest" and "re‑attest complete" are two different states with a real external event between them. We can't collapse them. But we can make them automatic: as soon as MAS acks, the state advances on its own — no operator click, no string‑match gate.
E. Practical migration path (so we don't rewrite everything in one weekend)
Freeze new writers. Make group.status only writable by one helper function. Anything that wants to change status calls a transition (e.g. transition.responseReceived(groupId)), never a raw UPDATE. This alone kills bug class #1.
Build the transition table as the single shared module, with tests that enumerate every (current state, leg shape) → legal next states. Frontend gates and server gates both import it.

Delete the audit script and the "must move together" comments — they exist only because the duplication exists.
This is roughly two tasks of plumbing + one task of UX cleanup, not a ground‑up rewrite. Most of the leg‑level code is fine; we're just removing the second vocabulary that sits on top of it.

VidaOS — Technical Architecture Review
A senior‑engineer walkthrough of how the system is actually built. No marketing — just what's in the repo and why.

1. System Overview
What it is. VidaOS is a multi‑tenant church operations platform. A single deployment serves many churches ("sites"), each with its own data, branding, permissions, and configuration. It bundles modules that have historically lived in separate SaaS products: Academy (LMS), Events, Giving, ChildHub (children's check‑in & safeguarding), Volunteers/Pipelines, Services planning, Watch (livestream/VOD), and a Global Admin surface for platform staff.

Core flows.

Member/staff app (index.html) — the day‑to‑day app.
Public surfaces (public.html) — public forms, watch pages, RSVP, giving links.
Global admin (global-admin.html) — platform tools for VidaOS operators.
Design principles you'll see repeated in the code.

Schema as the source of truth. A "Unified Module Schema" drives both frontend routes and backend mounting.
Tenant isolation at the database layer, not the application layer.
Capability‑based permissions rather than coarse roles.
Drift detection over documentation — many scripts/check-*.mjs enforce invariants in CI.
2. Architecture
Frontend
React 18 + Vite + TypeScript (with jsconfig for the older JS portions still in transition).
Routing. React Router 7. Routes are not hand‑mounted; they're generated from src/route-registry.js, which is itself derived from src/unifiedModuleSchema.js. That schema is also consumed server‑side, so a route can't drift between client and server without a CI check failing.
Three HTML entry points / bundles. index.html (member/staff), public.html (public/embed), global-admin.html (platform). Vite is configured for multi‑entry; this lets us ship leaner bundles to anonymous public surfaces and avoid leaking admin code paths.
State. TanStack Query for all server state (cache key conventions enforced); React Context for auth/UI.
UI. Radix primitives + Tailwind + Lucide. shadcn‑style component layer in src/components/ui.
Mobile. Capacitor 8 for iOS/Android wrappers — biometric auth, push, NFC for check‑in, live updates via @capawesome/capacitor-live-update.
i18n. src/i18n — English + Spanish today, structured for more.
Backend
Express 5 monolith (Node, ESM). It is intentionally a modular monolith, not microservices — see §8.
Phase‑based bootstrap in server/bootstrap.js: config → DB pool → migrations check → permission cache warm‑up → route registration → scheduler → listen. Each phase is observable and fails loudly.
Feature modules in server/routes/<feature>/ (academy, giving, childhub, volunteers, services, …). Business logic lives in server/services/<feature>/. Routes stay thin; services own invariants.
Lifecycle hooks in server/lifecycle/ for cross‑module side effects (e.g., a person being created in one module emitting events others can subscribe to).
Communication
Internally synchronous over function calls (monolith).
Cross‑module side effects use an in‑process event bus plus pg‑boss for anything that must survive a restart or be retried.
External: REST/JSON to clients; webhooks to Stripe, Twilio, SendGrid, Mux.
Infrastructure
Containerized via the included Dockerfile (@flydotio/dockerfile style) and a custom "Hydra" deployment harness in deploy/hydra/.
Sentry for error tracking; sourcemaps uploaded by a Vite plugin during build.
3. Data Layer
PostgreSQL is the single primary store. We deliberately avoided introducing a second datastore until forced to.
No heavy ORM. Drizzle is used for schema + Zod validation only. Queries go through a custom RLS‑aware query builder (server/db/pool.js) exposing scopedQuery(req, sql, params) that, per request, sets:
app.current_site_id
app.current_person_id
app.current_capabilities
Multi‑tenancy = Postgres Row Level Security. Every tenant‑scoped table has RLS policies keyed on app.current_site_id. A bug in application code cannot cross tenants — Postgres refuses. This is the single most important design decision in the system.
Schema is split by domain (schema-giving.js, schema-childhub.js, etc.) and assembled at boot. Migrations via node-pg-migrate in server/migrations/.
Caching. Deliberately minimal. The permission resolver has an in‑process LRU keyed by (personId, siteId, version) invalidated on permission writes. No Redis. We pay the Postgres round‑trip and keep the operational surface small.
4. Core Workflows
A) Authenticated request → data
Request hits Express. enrichRequestIdentity (server/auth/enrich.js) verifies the JWT access token, loads the Person, resolves their capabilities for the current site from the V2 permission tables, and attaches them to req.identity.
requireAuth (or requireStepUp for billing/sensitive ops) gates the route.
Handler calls a service. Service calls scopedQuery(req, …). The pool checks out a connection, sets the three app.* GUCs in the same transaction as the query, then runs it. RLS enforces tenant + ownership.
Response is shaped by a Zod output schema (where adopted) and returned.
Side‑effects (notifications, audit) are emitted on the in‑process bus; durable ones are enqueued to pg‑boss.
B) ChildHub check‑in (representative because it touches most subsystems)
Volunteer scans a guardian's NFC tag (Capacitor NFC plugin) or types a code; offline cache is consulted first.
Client posts a check‑in batch. Server validates against the active service window, the room ratios, and any safeguarding flags.
On success: write check‑in rows under RLS; emit childhub.check_in event.
Subscribers: notifications service (push/SMS to guardian), pipeline bridge (counts toward volunteer activity if the bridge toggle is on — see Task #597/#598), and the room capacity projector.
Escalations (e.g., a child unclaimed past pickup) are scheduled jobs in pg‑boss with pg_try_advisory_lock to keep multiple instances from double‑firing.
5. Scalability & Performance
Horizontal stateless app servers. All session/identity state is in JWTs + DB; instances are interchangeable.
Postgres is the scaling axis. RLS adds a measurable but predictable cost; we mitigate with careful indexing per tenant column and partial indexes on hot module tables.
Read patterns dominate. We favor narrow indexes and avoid SELECT * in services; many list endpoints support cursor pagination.
pg‑boss absorbs spiky write workloads (notifications, media render hooks, escalations). Concurrency is bounded per queue.
Bottlenecks identified.
Permission resolution under cold cache — addressed by the in‑process LRU and a permission‑version column that lets us bust narrowly.
Public surfaces under launch traffic — addressed by giving them their own entry bundle and aggressively cacheable endpoints.
Mux webhooks during livestream — handled idempotently with dedupe keys.
6. Reliability & Fault Tolerance
Sentry for app errors, with release + sourcemap correlation.
Structured logging tagged with siteId, personId, requestId (set in the enrich step). This is what makes multi‑tenant production triage possible.
Job retries via pg‑boss with backoff; failed jobs are visible and replayable.
Advisory locks for any work that must be singleton across instances (nightly backup, escalations).
Webhook idempotency for Stripe/Mux — we store provider event IDs and short‑circuit duplicates.
Drift checks in CI (scripts/check-*.mjs) catch schema/route/permission drift before deploy.
7. Security
AuthN. Custom JWT (access + refresh). MFA via TOTP, SMS/WhatsApp OTP, and Passkeys (@simplewebauthn).
Step‑up auth. requireStepUp enforces a fresh 15‑minute re‑auth window on sensitive actions (billing, permission grants, destructive admin ops).
AuthZ. V2 capability‑based permission system in server/permissions/. Roles are sugar over capability sets. Reads of role keys directly are forbidden and enforced by check:no-role-keys-reads.
Tenant isolation. Postgres RLS — see §3. This is the linchpin.
Secrets. Server‑only env; never read on the client. Stripe webhooks signature‑verified.
Adversarial test suite (tests/adversarial/) actively tries to bypass tenant boundaries, escalate permissions, and abuse public endpoints.
A threat_model.md lives at the repo root and is referenced by the policy‑staleness check.
8. Tradeoffs & Decisions
Modular monolith over microservices. Lower operational burden for a small team; cross‑module transactions stay trivial. The seams (services + lifecycle events) make extraction possible later if a module's load profile demands it.
No Redis. We avoid the second datastore. If pub/sub or rate‑limiting outgrows Postgres LISTEN/NOTIFY + pg‑boss, we'll add it then.
Drizzle for schema only, not as an active record. Keeps SQL explicit, RLS‑aware, and reviewable. We pay in verbosity.
Schema‑driven routing. Adds friction to "just add a route," but eliminates an entire class of client/server drift bugs.
Capacitor over a separate native codebase. One codebase, native shell where it matters (NFC, biometric, push).
What we deliberately did not build. No GraphQL, no service mesh, no event store, no microservice split, no in‑house feature flag system (we use a small in‑DB toggle table).
Known limitations. Permission resolution still has cold‑cache latency on first request after a deploy. Some legacy JS files are mid‑TS migration. The mockup sandbox is a separate Vite app under artifacts/mockup-sandbox and is not yet wired into the main test pipeline.
9. Developer Experience
Layout.
src/ — frontend.
server/ — backend (routes, services, db, auth, permissions, lifecycle, migrations).
shared/ — schemas/types shared across both.
artifacts/mockup-sandbox/ — isolated component preview.
tests/ (vitest + adversarial) and e2e/ (Playwright, including visual regression).
scripts/ and ci/baselines/ — drift/invariant checks.
Testing. vitest for unit/integration, vitest realdb against a real Postgres, Playwright for E2E and visual, plus the adversarial sweep. npm run test:all runs the full battery.
CI/CD. Multiple audit workflows (Adversarial, Dead Code, Guardrails, Platform Map, Playwright, Real DB, Vitest) — they're visible in this very environment. Deploys go through the Hydra harness; Sentry releases are tagged with the build SHA.
Onboarding. CLAUDE.md, replit.md, DECISIONS.md, and CONTRIBUTING.md in the repo root are the entry reading. The drift checks are unusually helpful for new engineers because they fail with actionable messages rather than mysterious runtime errors.
Where the hard questions usually land
"How do you prove a tenant can't see another tenant's data?" RLS plus the adversarial suite that asserts it.
"Why one Postgres for everything?" Operational simplicity wins until a workload proves otherwise; pg‑boss + LISTEN/NOTIFY have been sufficient.
"What happens when the permission cache is wrong?" Permission rows carry a version; writes bump it; resolvers key on (person, site, version), so stale entries are unreachable rather than dangerous.
"Why a custom query builder instead of an ORM?" Because RLS context must travel with every query in the same transaction, and we wanted that to be impossible to forget.

Architectural Choices Worth Highlighting
These are the decisions in this codebase that an experienced reviewer should walk away remembering. Each one is a deliberate trade made in the repo, not something we got for free.

1. Tenant isolation is enforced by Postgres, not by us
RLS policies + a scopedQuery builder that sets app.current_site_id / app.current_person_id in the same transaction as every query. A bug in application code cannot cross tenants — the database refuses. This is the single highest‑leverage decision in the system.

2. Schema is the source of truth, not convention
unifiedModuleSchema.js → route-registry.js drives both client routing and server route mounting. Drift between frontend and backend is a CI failure, not a runtime mystery. Adding a route has more friction; an entire class of bugs disappears.

3. Capability‑based permissions instead of roles
V2 permissions resolve to capabilities; roles are sugar. Direct reads of role keys are forbidden and enforced by check:no-role-keys-reads. New features ask "what capability does this need," never "is this user an admin."

4. Step‑up auth as a first‑class middleware
requireStepUp enforces a fresh 15‑minute re‑verification window on billing, permission grants, and destructive admin ops. Sensitive actions are gated structurally, not by ad‑hoc checks in handlers.

5. Drizzle for schema/validation only — explicit SQL everywhere else
We use Drizzle + Zod for the schema and request validation, but queries are hand‑written SQL through the RLS‑aware pool. We pay in verbosity; we keep queries reviewable, indexable, and impossible to accidentally run outside an RLS context.

6. Modular monolith with clean seams
Feature code lives in server/routes/<feature> + server/services/<feature>, with cross‑module communication going through a lifecycle event bus. Same process, same transaction where it matters — but the seams are real, so any module that outgrows the monolith can be extracted without a rewrite.

7. Durable jobs in Postgres (pg‑boss), not a second datastore
Background work, retries, scheduled jobs, and escalations all live in Postgres. No Redis, no SQS, no separate broker. pg_try_advisory_lock keeps singleton jobs singleton across instances. One operational surface; one backup story.

8. Idempotent webhooks by default
Stripe, Mux, Twilio, SendGrid event IDs are stored and dedup'd. Replays are safe. This is the kind of detail that only matters once — and only matters because we got it right.

9. Three frontend bundles instead of one
index.html (member/staff), public.html (anonymous public surfaces), global-admin.html (platform tools). Anonymous traffic doesn't download admin code; admin code is harder to accidentally expose.

10. CI checks as executable architecture documents
scripts/check-*.mjs (route registry drift, schema drift, permission grant integrity, freeze‑list hash, policy staleness, decision coverage, server timeout literals, no role‑key reads). The architecture is enforced by code, not by a wiki page everyone forgot to read.

11. An adversarial test suite, not just a unit test suite
tests/adversarial/ actively tries to bypass tenant boundaries, escalate permissions, and abuse public endpoints. Security invariants are tested as invariants, not assumed.

12. Structured request identity is set once, used everywhere
enrichRequestIdentity resolves person + capabilities + site at the edge, tags logs with siteId/personId/requestId, and feeds both the RLS context and the permission checks. Everything downstream — logs, permissions, queries — agrees on who is doing what.

13. Permission cache keyed on a version column
The in‑process LRU is keyed on (person, site, version). Permission writes bump the version. Stale cache entries become unreachable rather than wrong. Correctness is structural, not a TTL gamble.

14. Capacitor wrapper, not a parallel native codebase
One codebase ships web, iOS, and Android. Native plugins (NFC, biometric, push, live updates) where they earn their keep. We avoided maintaining two product surfaces.

15. Schema‑driven, decision‑logged
DECISIONS.md + a CI decision-coverage check keep architectural decisions discoverable and current. New engineers can read why something is the way it is, not just what it is.

How I'd frame it for the audience
"The decisions worth your attention are the ones that move correctness from runtime to compile/CI/database time: RLS for tenancy, schema‑driven routes, capability permissions, version‑keyed permission cache, drift checks in CI, and an adversarial suite. The rest of the system is conventional on purpose — Express, Postgres, React Query, pg‑boss — so the novel parts have room to be load‑bearing."

Good question — and worth being precise about, because "SOC 2" means different things depending on who's asking.

Compliance Posture — How to Talk About It
What SOC 2 actually is
SOC 2 is an audit of your organization against the Trust Services Criteria (Security, plus optionally Availability, Confidentiality, Processing Integrity, Privacy). It is not a feature you turn on, and it is not inherited from a vendor. You can't "be SOC 2" because you run on a SOC 2 platform — but you can inherit controls from one.

So the honest framing for a senior audience is two‑layered:

Layer 1 — Inherited controls (vendor SOC 2)
The platforms underneath us (managed Postgres, hosting, secrets) carry their own SOC 2 reports. In an audit those map to controls we'd otherwise have to implement and evidence ourselves: physical security, hypervisor isolation, backup infrastructure, encryption at rest on managed disks, key management for the managed services, datacenter access logging, etc. We reference the vendor reports; we don't re‑audit them.

Layer 2 — What we've actually built that maps to SOC 2 criteria
This is the part worth highlighting, because it's our work and it's already in the repo:

Security (CC — Common Criteria)

Logical access control: capability‑based permissions (V2), enforced server‑side, with check:no-role-keys-reads preventing regressions.
Tenant isolation: Postgres RLS — provable, testable, and exercised by the adversarial suite.
Authentication strength: JWT with refresh, MFA (TOTP / OTP / Passkeys), and step‑up re‑auth on sensitive actions.
Change management: drift checks (check-*.mjs), DECISIONS.md + decision‑coverage CI, freeze‑list hash, policy‑staleness check. Architectural intent is enforced, not aspirational.
Audit trail: structured logs tagged with siteId / personId / requestId; webhook events stored idempotently; lifecycle events recorded.
Vulnerability management hooks: dependency audit, SAST, and HoundDog scans available as a documented skill — runnable on demand and wireable into CI.
Secret management: server‑only env, never read on the client, separated per environment.
Availability

Stateless app servers (horizontally scalable).
Durable jobs in pg‑boss with retries and advisory locks.
Continuous WAL + 28‑day PITR on the managed Postgres (RPO ≈ seconds, RTO ≈ a console click).
Idempotent webhook handlers — replays don't corrupt state.
Confidentiality

RLS for tenant data segregation.
Step‑up auth gating sensitive read/write paths.
Three‑bundle frontend split keeps admin code off anonymous surfaces.
Processing Integrity

Zod validation on inbound payloads (and increasingly on outbound shapes).
Hand‑written SQL through an RLS‑aware pool — queries can't run outside the tenant context.
Adversarial suite continuously asserts cross‑tenant boundaries hold.
Privacy (if/when in scope)

The data model treats Person as the identity boundary; capability checks gate PII access.
Audit trails are person‑scoped, which is what you need for subject access / deletion requests.
What we don't have yet (and should be honest about)
A SOC 2 Type II audit needs evidence over a window — usually 6–12 months — of:

Access reviews (quarterly user + permission audits, with sign‑off).
Vendor management reviews.
Incident response runbooks with logged drills.
Change management approvals tied to tickets.
Background checks / security training records for staff.
Formal vulnerability management SLAs.
Business continuity / DR test results (not just capability — evidence of a drill).
A risk assessment, refreshed annually.
Written policies (Information Security, Acceptable Use, Incident Response, Data Classification, Vendor Management, BCP/DR).
These are organizational controls. The codebase can support them — it can't be them. An auditor will ask for the policies and the evidence, not the source code.

How I'd present this to a senior audience
"We're not SOC 2 certified — that's an organizational audit, not a code property. What we have done is build the technical controls a SOC 2 program would expect us to have: enforced tenancy at the database, capability‑based access with step‑up auth, structured audit logs, idempotent integrations, drift checks as enforced architecture, an adversarial test suite that asserts our security invariants, and managed Postgres with continuous PITR. When we choose to pursue Type II, the engineering work that usually slows audits down is already in place; what's left is policy, evidence collection, and access reviews."

That's the answer that lands well with technical reviewers — and also with a future auditor, because it's accurate.

We have a permission cache where it matters (the hottest read path).
We have indexes tuned per tenant column on the hot module tables.
We have cursor pagination on list endpoints.
We do not have Redis, and that's the deliberate part.
The path when Postgres becomes the bottleneck — and it should be stated explicitly:

Read replicas first. Neon supports them; routing read‑only handlers is mechanical because we already separate reads from writes at the service layer.
Materialized projections second — for things like room‑capacity, leaderboard‑style counts, and timeline aggregates. Already a pattern in ChildHub for room ratios.
Redis or equivalent only when (1) and (2) are insufficient, and only for ephemeral state (rate limits, presence, idempotency keys with short TTLs) — not as a primary store.
Per‑tenant query budgets / slow‑query alerting before any of the above, so we know which tenant or endpoint is actually the bottleneck.
Answer in a room: "Our caching is minimal because we're betting on Postgres scaling vertically + read replicas + projections before we add a second datastore. We'll add Redis when we have a workload that demands it — not before. Here's the order we'll add things in." That's a defensible plan rather than optimism.

4. Split event system — in‑process vs pg‑boss
The critic is exactly right that I didn't state the rule. The rule exists informally; it isn't enforced.

The rule we actually use:

In‑process bus — only for side effects that are (a) idempotent, (b) safe to lose on a crash, and (c) must observe the same transaction boundary as the originator.
pg‑boss — anything that must survive a restart, must be retried, must run on a schedule, must be singleton across instances, or crosses a transaction boundary.
Default when unsure: pg‑boss. Loss is worse than latency.
What's missing:

The rule isn't written down where engineers will see it.
No lint/CI check enforcing it (e.g., bus.emit from inside a handler that touches external systems should be flagged).
No naming convention distinguishing the two (e.g., emitLocal() vs enqueue()).
Honest answer: "The rule exists; the enforcement doesn't. We should rename the APIs to make the choice obvious at the call site and document the rule in DECISIONS.md with a coverage check." Cheap fix.

5. Capacitor + native features — fallbacks and offline conflicts
The critic is right; this was the thinnest part of my answer.

What we actually do today:

NFC has a manual code‑entry fallback when the tag read fails or the device lacks NFC.
Biometric has a passcode fallback (OS‑level) and ultimately falls back to password + MFA.
Offline check‑in queues batches locally and replays on reconnect.
What we don't yet have, and should be honest about:

A documented conflict resolution policy for offline replays beyond "last write wins / server validates against the active service window." For check‑ins specifically, the server currently rejects replays that conflict with a closed service window — which is correct but not graceful. There's no UI for the volunteer to reconcile.
Plugin compatibility matrix — which Capacitor plugins are tested on which OS versions, and the fallback when a plugin throws on a device.
Live‑update rollback — @capawesome/capacitor-live-update can push fixes, but we haven't drilled rolling one back.
Crash telemetry from the native shell is via Sentry, but we don't have a per‑device feature‑capability report (e.g., "12% of installs lack working NFC").
Answer in a room: "Fallback paths exist for the headline features — NFC → code entry, biometric → passcode → password+MFA, offline → queue + server‑side validation. What we don't have is a documented offline conflict policy or a plugin compatibility matrix, and we've never drilled a live‑update rollback. Those are real gaps."

6. Operational reality — rollback, migration safety with RLS, blast radius, observability under load
The critic is right that I waved at this. It deserves a fuller answer.

Rollback strategy.

Application: redeploy the previous build via the deploy harness; one click. Stateless app servers make this safe.
Data: we do not auto‑rollback schema. Forward‑fix migrations are policy. PITR exists for the worst case but is not a normal rollback tool.
Migration safety with RLS — this is genuinely subtle.

We require the expand → migrate → contract pattern for anything that changes a column type or drops a column under RLS.
New tables ship with RLS ENABLED and a policy in the same migration. We need a CI check that fails if a new tenant‑scoped table is added without both — that's a known gap (related to weakness #1).
Long‑running migrations are run in maintenance windows or behind a job, never inline at deploy.
Deploy blast radius.

Single environment per deploy; no canary or per‑tenant rollout today. For a true blast‑radius story we'd need either a percentage rollout or a per‑site feature flag (we have the latter; we don't gate releases on it consistently).
Observability under load.

Sentry for errors. Structured logs with tenant tags. Deployment log search.
What's missing: per‑endpoint p50/p95/p99 dashboards, per‑tenant request rate alerts, and slow‑query capture. These are real gaps and we should not pretend otherwise.
Honest answer: "Forward‑fix migrations as policy, expand/migrate/contract for breaking schema changes, RLS+policy required on every new tenant table (not yet CI‑enforced — gap), and no canary deploys today. Observability is event‑and‑log based, not metrics‑based; that's the next thing to add."

The Meta‑Point the Critic Made
"If you present this as 'look how advanced we are' you'll get dismantled. If you present this as 'here's a system with intentional tradeoffs and known risks' you'll gain respect."

That's the right framing and it should change how the deck reads. The revised opening line should be something like:

"I'll walk you through what we built, why, and — more importantly — what hasn't been stress‑tested yet and what will break first."

Engineers reward that kind of honesty. The deck currently doesn't earn it; it should.

Concrete Tasks This Critique Should Generate
Three of these are real engineering work that would meaningfully harden the system, not just narrative polish. With your approval I'd propose them as tasks for the implementing agent:

Make RLS bypass structurally hard. ESLint rule banning direct pool import outside the scoped wrapper, a CI check that every tenant‑scoped table has FORCE ROW LEVEL SECURITY + a policy, and adversarial tests that intentionally try to bypass and assert they fail. (Closes weakness #1 — the highest leverage one.)

Permission explainer endpoint + admin view. Returns resolved capabilities for a (person, site) with provenance (which role, which grant, which group, which version) and a recent‑change diff. (Closes weakness #2.)
